Codex 是一種可以直接在終端機裡協助你閱讀程式、修改檔案、執行命令與整理結果的 AI coding agent。和單純的聊天工具不同，它的價值不只是回答問題，而是能夠進入實際專案脈絡，幫你一起完成工作。

這篇文章會用最務實的方式，帶你完成第一次 Codex 協作流程：讀懂專案、修改檔案、驗證結果，最後整理成可提交的變更。

## Codex 可以幫你做什麼

如果你把 Codex 當成一位能在專案內協作的工程師，會比較容易理解它的正確用法。它特別適合下面幾種工作：

- 快速讀懂陌生 codebase
- 找出 bug 與風險點
- 直接修改程式與設定檔
- 補測試、跑 build、整理驗證結果
- 幫你寫文件、教學文與 migration note

但它不是萬能的。需求不清楚、上下文不足、驗證條件不明確時，產出品質通常會下降。所以你給的任務越具體，Codex 越容易穩定發揮。

## 開始前要準備什麼

至少要有三樣東西：

- 一個已存在的專案資料夾
- 可執行的本地開發環境
- 你希望完成的明確目標

例如下面這些請求通常都夠清楚：

- 幫我找出這個 blog build 失敗的原因
- 幫我新增一篇文章並確認 SEO metadata 正常
- 幫我把登入頁改成使用新的 API

相反地，像「幫我看看這個專案」就太空泛。Codex 仍然可以先探索，但你會得到比較鬆散的結果。

## 第一次協作怎麼下指令

一開始最好的做法不是直接叫它寫功能，而是先讓它建立上下文。

你可以這樣下：

```text
這是一個 blog，請先讀懂架構
```

或是：

```text
請先找出 build 失敗原因，再直接修正
```

這類要求的優點是明確、可驗證，而且讓 Codex 先觀察真實專案結構，而不是憑空猜測。

## 一個典型工作流

以下是一個很常見的協作流程：

1. 先描述目標，而不是直接描述解法。
2. 讓 Codex 掃描專案結構與關鍵檔案。
3. 要求它直接修改並驗證結果。
4. 最後請它總結改了什麼、還有哪些風險。

例如你要新增一篇文章到 Hugo blog，可以這樣說：

```text
請幫我寫一篇關於 Codex 教學的 markdown 文章，放到 blog，並確認 build 正常
```

這樣的任務有幾個好處：

- 輸入明確
- 輸出檔案清楚
- 可以立刻用 build 驗證
- 容易進一步延伸成 commit 或 deploy

## 讓 Codex 表現更好的技巧

### 1. 先給限制條件

限制條件越清楚，結果越穩定。例如：

- 不要改 theme 原始碼，優先用本地 override
- 文章請用繁體中文
- 修改完後請執行 `hugo`
- 幫我保留現有版型與命名風格

這比只說「幫我修一下」有效很多。

### 2. 指定驗證方式

如果你不要求驗證，很多問題會停留在「看起來合理」。實務上你應該要求它至少做一種驗證：

- 跑測試
- 跑 build
- 檢查產出的 HTML
- 檢查 git diff

例如：

```text
修完後請重新 build，並檢查 meta description、canonical 與 robots
```

### 3. 把大任務拆成幾步

不要一次丟太多需求。與其說：

```text
幫我重構整個網站、修 SEO、補文章、順便部署
```

不如拆成：

1. 先檢查目前 SEO 設定是否完整
2. 修掉 metadata 與結構化資料問題
3. 新增文章
4. 最後再處理 deploy

這樣比較容易控制品質，也比較容易審查每一步的變更。

## Codex 適合哪些人

如果你符合下面任一種情境，Codex 通常很有幫助：

- 你是工程師，想加快日常修改速度
- 你維護 side project，但不想每次都自己追整個專案脈絡
- 你在接手陌生專案，需要快速建立全局理解
- 你不是專職前後端工程師，但需要有人協助落地技術細節

它最強的地方，不是取代工程師，而是縮短從「我知道要做什麼」到「我真的做完了」之間的時間。

## 使用 Codex 時要注意什麼

有三件事不能偷懶：

### 要看 diff

即使變更看起來合理，也要檢查它到底改了哪些檔案。尤其是設定檔、部署流程、資料庫 migration 與權限邏輯。

### 要跑驗證

沒有驗證的修改，只能算草稿。至少要跑一次最接近實際情境的命令。

### 要保留判斷權

Codex 很擅長執行，但不應該代替你做產品判斷、架構取捨與風險承擔。你應該把它當成高效率協作者，而不是自動駕駛。

## 結語

如果你以前把 AI 當成問答工具，Codex 會是完全不同的使用體驗。它更接近一位能在專案中協作的工程師，可以幫你讀懂架構、改檔案、跑驗證、整理結果。

真正的關鍵不是「它會不會寫程式」，而是你能不能把任務描述成一個可執行、可驗證、可交付的工程問題。只要這件事做對，Codex 通常能帶來非常直接的效率提升。
